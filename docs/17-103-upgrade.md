# OPPO Pad Mini：保留 GBL＋KSU，从 500 升级 ColorOS 17.0.0.103 实测方案

实测日期：2026 年 10 月 14 日。整理日期：2026 年 10 月 15 日。

我这台 OPPO Pad Mini 已从 `OPD2515_16.0.10.500(CN01)` 升级到 `OPD2515_17.0.0.103(CN01)`，保留了 GBL 和 KSU。首次进入 GBL、启动 17、等待更新快照合并、再次正常重启，都已验证；之后把原来的 5 个模块全部开启并重启，系统和 root 仍正常。

这篇记录适用于**已经解锁、已有可用 GBL 和持久 KSU root** 的设备，重点是保留现有启动方式。它不包含首次提权或解锁教程，也不附通用一键刷写包。本文验证范围是下面这一组机型、固件和镜像组合。

## 一、实测环境与结果

| 项目 | 升级前 | 升级后 |
|---|---|---|
| 机型 | OPPO Pad Mini／OPD2515 | 同一台设备 |
| 系统 | 16.0.10.500(CN01) | 17.0.0.103(CN01) |
| Android | 16 | 17，SDK 37 |
| 内核 | 6.12.58-android16-6 | 6.12.69-android16-6 |
| KSU | 3.3.1，uapi 5，LKM 模式 | 3.3.1，uapi 5，LKM Live |
| 实际槽位 | b | a |
| 原始解锁状态 | unlocked／orange | 保持真实解锁 |

升级后确认 Shell 为 UID 0，SELinux 为 Enforcing，用户数据可以解锁，照片、文件和常用应用正常。系统已将 a 槽标记为启动成功，更新快照合并结束。

**b → a 是这次的实际情况，不是所有设备固定的升级方向。** 其他人必须读取自己的当前槽、目标槽和 OTA 状态，不能照抄分区后缀。

## 二、核心思路：旧 ABL、新 EFI、新 init_boot 各负责一件事

本次采用的启动链是：

```text
103 对应的 XBL
    ↓
保留的旧签名 ABL
    ↓
原有 GBL／BDS
    ↓
103 对应的 Normal EFI
    ↓
Android 17＋KSU
```

| 项目 | 这次怎么处理 | 作用 |
|---|---|---|
| 目标槽 `init_boot` | 用 103 原厂镜像重新修补 KSU | 保留 root |
| 目标槽 `abl` | 写回本机已使用的旧签名 ABL | 保留进入 GBL 的入口 |
| `ABL_normal.efi` | 换成从 103 原厂 ABL 提取并按 Normal 模式修补的新版 | 启动目标系统 |
| 原始 `efisp` 分区中的 BDS | 保留已有部署 | 提供 GBL 菜单 |
| `persist` 中的 EFI 文件和菜单 | 备份后更新 Normal EFI，保留旧 EFI 材料 | 让菜单指向正确的新版加载器 |
| XBL、xbl_config、TZ 等底层固件 | 使用官方完整 OTA 安装的版本 | 与新版系统配套 |

**“保留旧 ABL”不代表沿用全部旧启动文件。** 500 的 KSU 镜像和 500 的 Normal EFI 不能直接当成 103 对应的材料。

`ABL_normal.efi` 是从 ABL 中提取的 EFI 应用，不是可以直接刷进 `abl` 分区的完整分区镜像；原始 `efisp` 分区与 `/mnt/vendor/persist/efisp/` 文件夹也不是同一个东西。

本次选择 Normal Boot，使用真实解锁状态启动，没有新增 17 的 Fake Locked EFI。系统里显示 locked／green 的隐藏效果，也不能作为“真实 BL 已回锁”的证明。

## 三、升级前准备

1. **先备份重要数据。** 照片、文件、聊天记录和应用私有数据分别处理。启动分区备份不包含完整聊天和登录态。
2. **确认当前 root 稳定。** 在 KSU 中允许 Shell 获取 root，确认当前系统、内核、槽位和真实解锁状态。隐藏模块可能修改系统属性，解锁判断应结合原始 `/proc/bootconfig`。
3. **确认恢复入口。** 在当前系统下实际进入一次 GBL，确认所需的 USB fastboot 入口能用，再返回当前系统核对 root。菜单文件存在不能代替实测。
4. **暂停第三方模块。** 本次升级和最初两次开机时，Zygisk、LSPosed、隐藏和挂载等模块都处于暂停状态。先处理完排队的模块更新，再开始系统升级。
5. **准备完整包和对应材料。** 本次用 103 官方完整包，通过系统更新的“本地安装”入口安装。提前准备新原厂 `init_boot`、新原厂 ABL、新 KSU 镜像、新 Normal EFI，以及当前旧签名 ABL 和现用 EFI／菜单的备份。
6. **确保安装及重启可控。** 关闭设备提供的自动安装、夜间自动重启等选项，保持足够电量、存储空间和稳定的 USB 连接。升级过程中保持当前系统运行，安装结束先停在“立即重启”。

可以用下面的只读命令整理基本状态。先执行 `adb shell`，再执行 `su`；后续命令在同一个平板 root shell 中运行：

```sh
getprop ro.product.model
getprop ro.build.display.id
getprop ro.boot.slot_suffix
uname -r
id
/data/adb/ksud -V
cat /proc/bootconfig
```

分享这些输出前，应去掉序列号等设备标识。

## 四、先把 103 对应的材料准备好

### 1. KSU 使用新版原厂 init_boot

从 103 完整包的 `payload.bin` 提取原厂 `init_boot`，核对 payload 声明的长度和摘要，再用 KSU 3.3.1 修补。本次修补对象是 `init_boot`，没有换成通用 GKI `boot.img`。

虽然系统是 Android 17，目标内核仍属于 `6.12-android16-6` KMI，本次 LKM 选择对应的 `android16-6.12` 系列。不要只看系统大版本去选内核模块。KSU 的 LKM 安装方式和 KMI 说明见[官方安装文档](https://kernelsu.org/guide/installation.html)。

### 2. Normal EFI 使用 103 的原厂 ABL 生成

从 103 原厂 ABL 提取 LinuxLoader EFI，再生成 Normal Boot 变体。确认工具确实支持 Normal 模式，并核对日志中的真实状态透传、OPlus 警告处理和 fastboot 补丁结果；不能把默认输出的假回锁变体直接改名冒充 Normal EFI。

本次日志有 `Failed to patch ABL GBL`，同时 Normal 模式的 OPlus 补丁成功。这与目标 ABL 未发现原来的 GBL 加载标记相符，所以 GBL 入口由旧签名 ABL 保留。**这条警告只能结合这个目标版本、补丁日志和独立检查理解，不能把所有补丁警告一律忽略。**

### 3. 单独审查旧 ABL 与新固件

本次检查了 ABL、XBL、xbl_config、TZ、keymaster、UEFI 等关键镜像的签名及元数据；已解析的相关防回滚字段未发现上调。新 XBL 配合旧 ABL 是否能真正启动，最后仍靠本机开机验证。

未读取硬件熔丝，不能因此宣称可以随意降级。旧 ABL 方案受新版启动链和防回滚约束；上游也明确提示了相关风险，见[GBL OTA 说明](https://github.com/SuperTurtleDev/gbl_root_canoe/blob/8cc6fa5ad467af6d34a00f401290035ee87a14c7/wiki/docs/zh/ota.md)。

## 五、官方本地安装，完成后先不重启

在系统更新的“本地安装”中选择已校验的 103 完整包，等到安装完成、出现“立即重启”。

此时继续保持 USB 连接。重新读取实际目标槽，将目标槽的启动镜像、底层固件和本次完整包核对。**我这次不是看到重启按钮就直接刷旧 ABL：先核对了 47 项目标镜像范围、安装的 payload 元数据和原生更新引擎的适用性检查，再执行保留。**

这次完整包已被官方本地安装接受，所以没有为了安装更新而先恢复当前 b 槽的原厂 `init_boot`／ABL。其他设备如果被增量 OTA 的源分区校验拒绝，需要按自己的失败原因处理，不能把“先恢复原厂分区”或“无需恢复”当成所有更新的固定步骤。

### 本次遇到的特殊情况：安装完成，但目标槽尚未激活

本机更新器显示“立即重启”，但标准 UpdateEngine 状态仍是 `IDLE`，下次启动也仍指向旧 b 槽。进一步核对后确认：

- 更新器记录的目标是 103，本地安装和各项进度完成；
- `post-install-succeeded`、`verity-written` 都是 true；
- 缓存的 payload 元数据与本次完整包一致，原生适用性检查通过；
- a 槽的待启动镜像已经实际安装，只是更新器采用稍后激活方式。

因此，**不能单凭 `IDLE` 判断没有安装 OTA，也不能单凭“立即重启”认定目标槽已经激活。**

本次在备份、包校验和目标槽核对之后，暂停更新界面回调，通过系统 UpdateEngine 的 `setShouldSwitchSlotOnReboot`，携带该 OTA 的已认证元数据激活待启动槽。完成后才进入明确的 `UPDATED_NEED_REBOOT (6)`，下次启动为 a，a 可启动，当前仍是 b。

这是系统更新引擎提供的激活流程，相关实现见[AOSP 源码](https://android.googlesource.com/platform/system/update_engine/+/android16-release/aosp/update_attempter_android.cc)。**尚未完成安装、元数据不符或状态不明时，不能用手动切槽强行代替这个判断。** 本文不把这个分支压缩成一条脱离检查条件的通用命令。

## 六、在当前系统内完成目标槽保留

以本次实际的 b → a 为例，写入前先导出、校验并在电脑留存：

- 目标 a 槽刚安装的原厂 `init_boot`、完整 ABL 分区；
- 现用 Normal EFI、GBL 菜单及必要的原始 BDS 材料；
- 当前 b 槽的启动镜像和相应校验记录。

本次执行的保留内容是：

1. 将 103 对应的 KSU 修补镜像写入 `init_boot_a`。
2. 将已核对的旧签名 ABL 写入 `abl_a`。
3. 在 `/mnt/vendor/persist/efisp/` 中保存旧 Normal EFI 为 `ABL_500.efi`，保存新版本为 `ABL_17.efi`，将 `ABL_normal.efi` 更新成同一份 103 Normal EFI，并让 Normal Boot 菜单指向它。
4. 对写入后的两个原始分区、EFI 文件、菜单逐项回读并核对 SHA256，确认当前 b 槽的启动分区和原有 BDS 未被保留操作修改。

共享的 persist 文件不会跟着 A/B 槽自动回退，更新 EFI 时必须同时考虑默认启动项和旧文件的保存方式。写入应使用有状态检查、备份和失败处理的流程；**本文给出分区与文件清单，不附硬编码 a/b、跳过检查的通用 dd 脚本。**

本次保留操作没有再次刷原始 `efisp`／BDS，没有锁 BL、修改 ARB、清数据，也没有把 XBL／TZ 等底层固件强行换回旧版。新版底层固件由官方 OTA 安装。

只有全部写入、同步和回读确认完成，且待启动槽及 OTA 状态仍符合计划，才进入重启步骤。报错或读回不一致时，先停在当前系统中检查，不能靠反复重启碰运气。

## 七、首次开机、快照合并与再次重启

1. 按住音量上键，发起正常重启。出现 GBL 菜单后松开，先确认菜单确实出现，不操作 Lock、Unlock 或 ARB。
2. 选择指向新版 EFI 的 **Normal Boot**，等待首次 Android 17 启动并解锁屏幕。
3. 核对实际版本、当前槽位、新内核、KSU、Shell root 和用户数据。仅看到 GBL 菜单不足以确认新系统已成功启动。
4. 等待系统完成更新快照合并。合并期间不手动切槽、不擦除 userdata／metadata。本次由 MERGING 转为 NONE 后，才继续下一次验证。
5. 再做一次正常重启，不按音量键，确认默认启动项进入 17，root 仍在。
6. 最后恢复第三方模块，逐项验证。我的这台在基础升级确认后全部开启了原来的 5 个模块并重启，系统和 root 仍正常，也读到了 Zygisk／LSPosed 相关进程；这不能替代其他人的模块组合测试，也不代表每个应用里的 Hook 和隐藏效果都已测完。

本次最终核对结果：

```text
系统：OPD2515_17.0.0.103(CN01)
Android：17 / SDK 37
槽位：a
内核：6.12.69-android16-6-g242e1a07f878-ab15865446-4k
KSU：ksud 3.3.1 (uapi: 5)，LKM Live
Shell：UID 0
SELinux：Enforcing
用户数据：已解锁，照片/文件/常用应用正常
更新快照：合并完成
再次正常重启：通过
```

## 八、失败时的恢复边界

| 状态 | 可以考虑的处理 | 前提与限制 |
|---|---|---|
| 还在旧系统中，保留操作报错 | 按本次事务备份恢复刚修改的内容 | 先确认状态没变；这不是撤销整个 OTA |
| GBL／允许刷写的 fastboot 仍可进入，系统启动失败 | 检查新版 EFI、KSU 镜像，必要时恢复目标版本的原厂启动材料 | 要确认入口确实允许刷相关分区；不能把 500 的 boot/init_boot 混刷进 17 |
| 模块开启后出现异常 | 有 root 时停用问题模块，再定位 | 与 GBL 本身无法加载是不同层级的问题 |
| 新 XBL 根本无法启动旧 ABL，GBL 也进不去 | 需要另外核实低层恢复通道 | 本次没有验证这台设备的 EDL/9008 救砖方案，现有备份不能保证此时写得回去 |

**旧 b 槽、旧 EFI 和分区备份是恢复材料，不是“必定无损退回 500”的保证。** 特别是更新快照合并结束后，不能把旧槽当成可以随意切回的完整旧系统。

## 九、以后跟官方更新怎么做

本次成功说明这台 OPD2515 的 **500 → 17.0.0.103**，可以用“官方完整 OTA＋旧 ABL/GBL＋目标版本 Normal EFI＋目标版本 KSU”完成升级。

后续每个版本仍应按以下顺序处理：

```text
备份与包审查
→ 准备目标版本的新 KSU 和新 Normal EFI
→ 官方安装，完成后停在重启前
→ 核对实际源/目标槽和 OTA 激活状态
→ 备份、保留旧 ABL/GBL、写入目标版本 KSU/EFI并回读
→ 首次启动验证
→ 等快照合并
→ 正常重启复核
→ 恢复并测试模块
```

这次没有使用旧版 OTA Helper RC2，也没有验证“装一个模块后，所有未来更新都自动保 root”。本地执行工具固定于本次源版本、目标版本、槽位和镜像摘要，不能直接套到下一次 OTA。

增量更新还涉及精确的原厂源分区和 KSU 原厂备份登记。本次电脑修补镜像没有完成那套恢复登记验证，所以本文不宣称管理器的“恢复原厂镜像”一定可用，或未来增量 OTA 一定能过校验。KSU 的原厂备份与镜像内标记需要配套，见[官方说明](https://kernelsu.org/guide/installation.html#use-the-manager)。

## 附：本次材料的 SHA256

这些摘要用于识别本次实际使用的文件，不代表可跨机型、跨系统版本使用；自行重新修补产生的文件应重新审查，而不是仅凭文件名判断。

| 文件 | 大小 | SHA256 |
|---|---:|---|
| 103 官方完整 ZIP | 9,214,591,270 字节 | `aeeb3029c64f3a7251bf861325a21388c1817739c8684155ba7daa71f6beb8d5` |
| 103 原厂 init_boot | 8,388,608 字节 | `202332d30498b52967da93e1272a871161ec04e4e5825c7b541cddcce9a64516` |
| 本次 KSU 3.3.1 修补 init_boot | 8,388,608 字节 | `ddd0e19a562a33040f99282e23db848b4371d66b88581952843be33bfd516fc3` |
| 本次旧签名 ABL 完整镜像 | 1,048,576 字节 | `0210487cbc59bdcdb03bb2ee61d9d80fffad8f2ccf35bc7d28d7d9569ad59802` |
| 本次 103 Normal EFI | 782,336 字节 | `2efe7efced64c4caaea203277245e16ff0523e800a82ff87cc44642f8b3f4170` |

完整 ABL 分区备份与 OTA 中 ABL 文件的长度可能不同，不能直接拿不同范围的摘要作比较；应按声明的镜像范围核对，再按实际分区边界制定写入和回读方案。

Windows 下导出镜像时使用二进制安全的方式；部分 PowerShell 文本重定向方式会破坏二进制流。自己实现 Android 侧校验脚本时，也应在实际 shell 中验证：槽位返回值可能含制表符，`hash` 还可能是 shell 别名。本次脚本已针对这两项修复并完成实机验证。
